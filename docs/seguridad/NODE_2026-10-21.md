# Boletín de seguridad de Node.js del 21/10/2026 · D-149

**Fuente:** [Wednesday, October 21, 2026 Security Releases](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)
· **Línea afectada:** 22.x · **Versión parcheada:** **v22.23.4** · **El proyecto fijaba:** 22.22.2
(`.nvmrc`) con un suelo de `>=22.11.0` (`engines`)
· **Aplicada:** 2026-10-29, en la rama `etapa-15-node-22-23-4-seguridad`. Rige en `develop`
cuando se fusione su PR.

## 1 · Qué cambia

| Fichero                                         | Antes           | Después         |
| ----------------------------------------------- | --------------- | --------------- |
| `.nvmrc` (lo lee la CI con `node-version-file`) | `22.22.2`       | `22.23.4`       |
| `package.json` → `engines.node`                 | `>=22.11.0 <23` | `>=22.23.4 <23` |

**El cambio de seguridad es el suelo, no `.nvmrc`.** `.nvmrc` dice qué Node usa el equipo
y la CI. `engines` dice cuál se admite, y `scripts/lib/verificar-entorno.mjs` lo hace
cumplir en el paso 1 del verificador. Con el suelo viejo, un Node 22.22.2 seguía pasando
la comprobación del entorno: la diferencia con `.nvmrc` era sólo un aviso. La sonda 6 bis
de `pruebas-negativas.mjs` (`sondas/node-del-boletin.mjs`) demuestra el cambio en los dos
sentidos:

- con el `engines` nuevo, un Node 22.22.2 hace fallar la comprobación;
- con el `engines` anterior, ese mismo Node pasaba.

**No hay nada que recompilar.** El proyecto no tiene módulos nativos. El Edge usa
`node:sqlite`, el que viene con el runtime (ADR-017), no `better-sqlite3`. Por eso la
actualización de SQLite del boletín llega al Edge con el propio Node.

**Descarga verificada** (la usada para la verificación local en Linux):

- el SHA-256 de `node-v22.23.4-linux-x64.tar.xz` coincide con `SHASUMS256.txt`;
- `SHASUMS256.txt.sig` lleva una firma válida de la clave
  `5BE8A3F6C8A5C01D106C0AD820B1A390B168D356` (Antoine du Hamel), que figura entre las
  claves de publicación del README de `nodejs/node`.

**Componentes incluidos.** Medidos con `process.versions`:

| Componente | 22.22.x medido | 22.23.4 |
| ---------- | -------------- | ------- |
| OpenSSL    | 3.5.4          | 3.5.9   |
| undici     | 6.23.0         | 6.29.1  |
| c-ares     | 1.34.6         | 1.34.9  |
| SQLite     | 3.50.4         | 3.53.4  |
| Brotli     | 1.1.0          | 1.1.0   |

Brotli no cambia de versión: el arreglo de CVE-2026-111497 es un parche sobre la copia que
lleva Node. La columna «22.22.x» se midió con el Node 22.22.0 del contenedor de
verificación; la 22.22.2 que fijaba `.nvmrc` no estaba instalada.

**El experimento de CVE-2026-111497**, con la 22.22.0 del contenedor y sin explotar nada,
sólo para ver si el descompresor se alcanza:

- **Vía de los equipos:** un servidor HTTP que responde `Content-Encoding: br` a un
  `fetch` que pidió `gzip, deflate`. `fetch` devuelve el texto descomprimido.
- **Vía de la API:** `express.json()` recibe un POST con un cuerpo comprimido en Brotli.
  El manejador recibe el objeto ya descomprimido, con 200.

## 4 · Una regresión que trae 22.23.4, y su corrección en este PR

**[Probable] Con Node 22.23.4 (undici 6.29.1), el proxy de la consola perdía a veces el
PRIMER trozo del cuerpo de una petición.** El paso 13d del verificador falló: «Mi rostro»
recibió de la API un 400 «Unexpected token 't', "t6mTjFAusl"… is not valid JSON».

| Prueba                                                                                | Resultado                                                                                             |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Recorrido del residente con el proxy original (`body: peticion.body, duplex: 'half'`) | 22.23.4: **5 de 11 en rojo** · 22.22.0: **0 de 9**, siempre con el mismo prefijo truncado             |
| Espía TCP entre la consola y la API                                                   | El `POST /mi/rostro` ya **sale truncado de la consola**: el primer trozo `chunked` empieza en «t6mT…» |
| El cuerpo leído en el proxy antes de dárselo a `fetch`                                | 22.23.4: **8 de 8 en verde**                                                                          |
| Las dos reproducciones mínimas (undici con un flujo; el clonado de Next, aislado)     | 0 de 30 y 0 de 40 en ambas versiones: hace falta la combinación real de Next 15.5 + undici 6.29.1     |

**[Cierto] Corrección:** `apps/web/src/lib/cuerpo-acotado.ts`.

- El proxy lee el cuerpo entero y reenvía los bytes; ya no le pasa a `fetch` un flujo.
- Leerlo exige un tope propio de **3 MiB**, por encima de la foto (2200 kB en la API).
- Con un cuerpo mayor, la consola responde 413 sin llamar a la API.

Comprobado: tras la corrección, el recorrido pasa **8 de 8** con 22.23.4. Las respuestas siguen
saliendo en flujo, porque el canal SSE depende de ello.

[Suposición] No he localizado el cambio concreto de undici que lo provoca. La corrección no
depende de encontrarlo: el proxy ya no entrega flujos de petición a `fetch`.

## 5 · Lo que la actualización NO cierra, y su PR aparte

La actualización arregla este fallo del descompresor, pero no quita la superficie: la API
seguía pasando a `node:zlib` cualquier cuerpo comprimido, antes de los guards. Se cierra
en **D-150**, [PR #72](https://github.com/4rg3n15/NextResidential/pull/72), por decisión
del cliente (2026-10-29):

- `inflate: false` en los seis parsers de la tubería: `json` (tres), `urlencoded`, `raw`
  del audio y `text` del SDP;
- `bodyParser: false` en `main.ts`.

Un cuerpo comprimido es un 415 y no llega al descompresor, sea cual sea la versión de
Node. Ningún cliente legítimo los envía.
